# AI销管王 PRD：需求拆解、优先级与技术闭环

## 1. 结论先行

AI销管王不是单纯的 CRM，也不是单纯的 AI 分析工具，而是围绕“销售专用手机数据采集 -> AI分析 -> 销售执行 -> 管理督导 -> 数据再回流”的销售过程管理系统。

从技术角度看，原型里把“租户管理”放到 Phase 3 更像是从产品售卖视角切分的阶段，但如果系统未来要对外商业化，多租户不能等到第 3 阶段再补。正确做法是：

- P0 就建设租户底座：数据模型、权限边界、配置隔离、审计隔离必须从第一天存在。
- P0 不一定暴露完整租户运营后台：可以先单租户运行，但数据库和服务层默认带 `tenant_id`。
- P2 再开放商业化租户功能：租户列表、套餐计费、租户开通、版本权限、客户成功运营等。

否则后期从单租户改多租户，会牵涉客户、沟通记录、AI结果、通话录音、微信消息、订单、权限、审计、知识库、规则配置的全链路迁移，成本和风险都很高。

## 2. 产品目标

### 2.1 业务目标

- 降低销售主管人工盯过程的成本。
- 提升销售对高意向客户的响应速度。
- 把销售手机里的电话、微信沟通数据结构化，形成可追踪的客户时间线。
- 用 AI 自动识别客户意向、风险信号、合规风险和下一步动作。
- 为后续商业化 SaaS 输出可复用的销售管理底座。

### 2.2 用户目标

- 销售：每天知道先跟谁、怎么跟、为什么跟。
- 管理者：知道团队风险在哪里、谁需要辅导、哪个客户需要介入。
- 管理员：能配置数据源、规则、权限、脱敏、知识库和组织结构。
- 企业客户/租户：能独立使用一套隔离的数据、规则、权限和流程。

### 2.3 成功指标

| 指标 | MVP目标 | 说明 |
|---|---:|---|
| 销售手机数据同步成功率 | >= 95% | 电话、微信、设备状态同步 |
| 通话/微信记录客户匹配准确率 | >= 90% | 能正确归属到客户或待人工确认 |
| 高意向客户提醒召回率 | >= 80% | 不遗漏主要高意向信号 |
| 高意向客户24小时内跟进率 | 提升30% | 对比上线前基线 |
| AI建议人工采纳/确认率 | >= 60% | 销售或管理者认可 |
| 数据权限/脱敏事故 | 0 | 尤其是微信、电话、手机号 |
| 管理者每周风险处理闭环率 | >= 80% | 风险有处理状态和结果 |

## 3. 用户角色

| 角色 | 核心诉求 | 主要功能 |
|---|---|---|
| 销售 | 明确今日优先级，提升跟进效率 | 今日工作台、客户管理、客户详情、AI建议、日报周报 |
| 销售主管/管理者 | 看清团队过程，及时干预风险 | 团队总览、漏斗诊断、AI参谋、线索分配、客户交接 |
| 管理员/运营 | 配系统、配规则、看同步和审计 | 组织权限、数据源健康、AI规则、脱敏、知识库、审计 |
| 企业租户管理员 | 管理本企业人员、流程、套餐 | 租户配置、流程配置、版本权限，P2开放 |
| 平台运营 | 商业化交付和客户成功 | 租户列表、套餐计费、用量监控，P2开放 |

## 4. 关键判断：阶段应按“底座能力”而不是“页面出现时间”拆

### 4.1 原型阶段的问题

原型里的 Phase 1/2/3 更偏演示与售卖节奏：

- Phase 1：内部试点。
- Phase 2：功能补全。
- Phase 3：商业化。

但开发不能完全照这个节奏切，因为部分 Phase 3 能力其实是底层架构前提，例如：

- 多租户隔离。
- 租户级配置。
- 权限与脱敏策略。
- 审计日志。
- 数据源配置。
- AI规则配置。

这些能力如果晚做，会导致 P0/P1 产生大量单租户硬编码，后续重构代价极高。

### 4.2 推荐阶段

| 阶段 | 定位 | 原则 |
|---|---|---|
| P0 技术底座 + 业务最小闭环 | 先跑通销售手机数据到AI再到销售/管理动作 | 底层多租户，前台可单租户 |
| P1 业务增强 + 管理提效 | 补齐管理、成长、提成等高频业务 | 基于 P0 数据闭环扩展 |
| P2 商业化 SaaS | 开放租户运营、套餐计费、客户成功 | 不重构底座，只开放运营能力 |

## 5. 业务主流程

### 5.1 线索到客户跟进闭环

1. 千川、百度、腾讯、公海、老客户介绍或手动录入产生线索。
2. 管理者或系统自动分配线索给销售。
3. 线索进入销售“最近分配”和“客户管理”。
4. 销售用专用手机拨打电话、加微信、发送资料、邀约课程或推进报价。
5. 手机 Agent 采集电话、录音、微信消息、设备状态。
6. 系统进行客户匹配、去重、脱敏、转写和结构化。
7. AI 识别意向、预算、决策链、风险、下一步动作。
8. AI 结果回写客户详情、销售待办、管理看板。
9. 销售继续执行，管理者对风险客户或异常销售发起督导。
10. 新的执行结果再次从手机回流，形成闭环。

### 5.2 AI分析闭环

1. 原始数据进入：电话录音、通话记录、微信消息、客户资料、订单物流。
2. 数据治理：清洗、脱敏、客户归属、时间线合并。
3. AI任务：摘要、意向识别、信号提取、风险词识别、行动建议。
4. 人工反馈：销售确认“有用/无用”、管理者处理风险、管理员调规则。
5. 反馈沉淀：AI结果和人工反馈都写入数据库，供后续调参和评估。

### 5.3 管理闭环

1. 管理者查看团队总览和 AI 参谋。
2. 系统展示高意向未跟进、合规风险、漏斗卡点、资料缺失、设备异常。
3. 管理者创建督导、重新分配线索、抽查录音、安排培训或介入客户。
4. 销售处理后更新状态。
5. 风险关闭，处理记录进入审计和复盘。

## 6. 需求优先级总表

优先级定义：

- P0：没有它，业务闭环或技术底座无法成立。
- P1：业务价值明确，但可在 MVP 后补齐。
- P2：商业化、规模化、精细化能力。
- P3：锦上添花或依赖更多真实数据后再做。

### 6.1 P0：MVP必须做

| 模块 | 需求 | 优先级 | 原因 |
|---|---|---:|---|
| 多租户底座 | 所有核心表预留 `tenant_id`，服务层默认按租户隔离 | P0 | 后期补成本极高 |
| 组织与权限 | 用户、角色、团队、销售归属、数据范围 | P0 | 决定客户和沟通记录谁能看 |
| 数据脱敏底座 | 手机号、微信号、聊天记录、录音按角色脱敏 | P0 | 涉及敏感数据和合规 |
| 销售手机设备绑定 | 设备ID、绑定销售、微信账号、在线状态 | P0 | 手机是核心数据源 |
| 电话数据采集 | 通话时间、方向、时长、录音、转写状态 | P0 | AI分析的主数据 |
| 微信数据采集 | 微信联系人、消息、文件/语音元数据、加微状态 | P0 | 客户意向和风险的重要来源 |
| 数据接入与治理 | 客户匹配、去重、脱敏、时间线合并、异常队列 | P0 | 不治理数据，AI不可用 |
| 线索导入 | Excel/CSV导入千川、百度、腾讯等线索 | P0 | API可后置，先跑业务 |
| 线索分配 | 管理者手动分配，系统记录分配历史 | P0 | 销售工作入口 |
| 客户管理 | 客户列表、客户详情、阶段、归属、最近跟进 | P0 | 核心业务对象 |
| 沟通时间线 | 电话、微信、手动记录统一展示 | P0 | 销售和管理者判断依据 |
| AI客户摘要 | 基于沟通记录生成客户摘要和下一步建议 | P0 | 产品差异化核心 |
| AI意向识别 | 高/中/低意向、置信度、关键信号 | P0 | 工作台和管理看板依赖 |
| 销售今日工作台 | 高意向、逾期、主管指派、AI建议 | P0 | 销售每日使用场景 |
| 管理者团队总览 | 团队指标、高意向未跟进、风险提醒 | P0 | 管理价值闭环 |
| AI规则基础配置 | 意向阈值、风险词、跟进频率、ABC分类 | P0 | AI结果必须可调 |
| 审计日志 | 配置变更、敏感数据查看、客户转移、导出 | P0 | 管理和合规底座 |
| 系统健康 | 设备离线、微信延迟、API异常、转写失败 | P0 | 数据质量保障 |

### 6.2 P1：试点增强

| 模块 | 需求 | 优先级 | 原因 |
|---|---|---:|---|
| 自动分配规则 | 按团队、销售负载、客户类型分配 | P1 | 提效，但手动分配可先替代 |
| 订单物流 | 订单导入、物流状态、客户详情展示 | P1 | 对部分业务重要，但非AI闭环核心 |
| 漏斗诊断 | 线索到成交六阶段转化和卡点 | P1 | 管理价值强，依赖稳定业务数据 |
| AI参谋 | 风险聚合、作战建议、客户匹配建议 | P1 | 需要 P0 数据积累 |
| 客户交接 | 客户、记录、任务、风险转移 | P1 | 重要管理场景 |
| 销售个人复盘 | 日/周/月报、能力短板、跟进质量 | P1 | 增强销售粘性 |
| 营销弹药库 | 话术、案例、资料推荐 | P1 | 与AI建议联动，提高执行质量 |
| 排名 | 销售业绩和过程排名 | P1 | 管理常用，但不是底座 |
| 知识库管理 | 内容上传、分类、权限 | P1 | 支撑弹药库和AI推荐 |

### 6.3 P2：商业化与规模化

| 模块 | 需求 | 优先级 | 原因 |
|---|---|---:|---|
| 租户运营后台 | 租户列表、新建租户、停启用、到期日 | P2 | P0有底座，P2开放运营 |
| 套餐与计费 | 低配/中配/顶配、席位、用量、功能开关 | P2 | 商业化售卖需要 |
| 租户级流程配置 | 不同行业/客户配置不同销售阶段 | P2 | 对外客户差异化 |
| 租户级AI规则模板 | 行业模板、规则复制、默认词库 | P2 | 降低交付成本 |
| 提成核算 | 订单提成、分账比例、佣金规则 | P2 | 价值高，但依赖订单准确性 |
| 销售成长中心 | 课程、考试、AI陪练、错题 | P2 | 培训体系，非MVP闭环 |
| 客户成功看板 | 租户活跃、设备在线、AI使用、续费风险 | P2 | SaaS运营需要 |

### 6.4 P3：后续优化

| 模块 | 需求 | 优先级 | 原因 |
|---|---|---:|---|
| 高级预测模型 | 成交概率、流失概率、销售能力预测 | P3 | 需要大量历史数据 |
| AI自动生成作战计划 | 多客户、多销售、多目标自动排兵布阵 | P3 | 依赖规则和样本验证 |
| 深度CRM替代能力 | 合同、回款、复杂审批 | P3 | 当前定位不替代重CRM |
| 多渠道自动触达 | AI自动发微信/短信/外呼 | P3 | 合规和业务风险高 |

## 8. MVP范围

### 8.1 MVP包含

- 单租户可运行，但底层所有核心表和服务必须支持多租户。
- 销售手机设备绑定和状态监控。
- 电话、微信数据采集接口与数据入库。
- 通话转写状态管理，允许先接第三方转写或预留接口。
- 线索导入、手动分配、销售客户列表。
- 客户详情：客户档案、沟通时间线、AI摘要、意向等级。
- 销售今日工作台：高意向、逾期未跟进、AI建议。
- 管理者团队总览：关键指标、风险客户、异常同步。
- 管理后台：组织权限、AI规则、脱敏策略、数据源健康、审计日志。

### 8.2 MVP不包含

- 完整套餐计费。
- 对外租户开通流程。
- AI陪练和培训通关。
- 自动佣金结算。
- 复杂合同/回款/审批。
- AI自动外呼或自动发微信。
- 深度替代企业现有CRM。

## 9. 功能需求明细

### 9.1 租户与权限底座

#### 用户故事

作为平台开发者，我希望所有业务数据天然按租户隔离，这样未来从内部试点扩展到商业化时不需要重构核心表。

#### 功能要求

- 所有核心业务表包含 `tenant_id`。
- 用户登录后解析租户上下文。
- 服务层查询默认附加租户过滤。
- 管理员可配置角色和数据范围。
- 敏感字段按角色脱敏。
- 所有敏感操作写审计日志。

#### 验收标准

- 不同租户用户无法通过接口查询到对方客户、沟通记录、订单、AI结果。
- 销售只能看本人客户；主管可看团队；管理员按配置查看。
- 脱敏规则变更有审计记录。

### 9.2 销售手机数据采集

#### 用户故事

作为销售主管，我希望系统能从销售专用手机自动拉取电话和微信沟通记录，这样不用依赖销售手动填写跟进记录。

#### 功能要求

- 设备绑定：设备ID、销售、微信号、在线状态。
- 电话采集：呼入呼出、号码、时间、时长、录音地址、转写状态。
- 微信采集：联系人、消息、时间、消息类型、文件元数据。
- 同步监控：最近同步时间、延迟、失败原因。
- 异常处理：设备离线、同步失败、客户未匹配进入待处理队列。

#### 验收标准

- 新通话/微信记录可在限定时间内进入原始数据区。
- 设备离线超过阈值产生告警。
- 未匹配客户的数据不丢失，进入人工校验队列。

### 9.3 客户与沟通时间线

#### 用户故事

作为销售，我希望打开客户详情就能看到这个客户最近所有电话和微信沟通，这样我能快速判断下一步怎么跟。

#### 功能要求

- 客户基础信息：公司、联系人、职位、行业、规模、来源、归属销售。
- 客户阶段：线索、商机、有效商机、需求确认、方案报价、成交。
- 统一时间线：电话、微信、手动记录、订单物流、AI信号。
- 客户状态：正常、不感兴趣、明确拒绝、电话不接、投诉风险。
- 星标和高意向标识。

#### 验收标准

- 同一客户的电话和微信记录按时间顺序展示。
- AI信号能定位到原始沟通记录。
- 客户阶段变更有记录，支持回溯。

### 9.4 AI分析

#### 用户故事

作为销售，我希望系统自动总结客户意向和下一步动作，这样我不用翻历史聊天和录音。

#### 功能要求

- 客户摘要：当前状态、需求、顾虑、关键人、下一步。
- 意向识别：高/中/低，置信度。
- 信号识别：预算、决策链、采购意向、紧迫度、竞品、异议。
- 风险识别：超时未跟进、合规风险词、投诉风险、断联。
- 建议生成：下一步跟进动作、话术建议、资料推荐。
- AI反馈：有用/无用、人工确认、人工修正。

#### 验收标准

- AI结果必须保留来源引用，能追溯到电话或微信记录。
- 低置信度结果标记为“待确认”，不能直接覆盖关键业务字段。
- 风险词命中能触发管理者提醒。

### 9.5 销售工作台

#### 用户故事

作为销售，我希望每天进入系统后直接看到今天最该处理的客户和动作。

#### 功能要求

- AI今日摘要。
- 综合优先级清单。
- 高意向客户待办。
- 逾期未跟进提醒。
- 主管指派任务。
- 一键跳转客户详情。
- 日报/周报/月报生成。

#### 验收标准

- 每条待办可追溯来源：AI提取、主管指派、规则触发或手动创建。
- 待办完成后状态回写。
- 超时待办进入管理者风险视图。

### 9.6 管理者看板

#### 用户故事

作为销售主管，我希望系统自动告诉我团队里哪些客户、销售和流程有风险。

#### 功能要求

- 团队总览：线索、跟进、有效沟通、高意向、成交预测。
- 高意向未跟进列表。
- 销售异常：跟进少、转化低、资料缺失、设备离线。
- 风险列表：过程风险、合规风险、数据异常。
- 管理动作：创建督导、抽查录音、重新分配、客户交接。

#### 验收标准

- 每个风险有等级、触发原因、涉及销售、客户、建议动作。
- 管理动作有处理状态和处理结果。
- 已处理风险可关闭并进入审计。

## 10. 非功能需求

### 10.1 安全与合规

- 电话录音、微信聊天记录、手机号、微信号属于敏感数据。
- 存储需加密或至少对敏感字段加密。
- 导出必须应用当前角色脱敏规则。
- 敏感数据访问必须记录审计日志。
- AI分析使用的数据需要遵守租户隔离。

### 10.2 性能

- 销售工作台首屏 P95 响应小于 2 秒。
- 客户详情时间线 P95 响应小于 3 秒。
- 手机同步延迟目标小于 5 分钟，允许异步处理AI。
- AI分析允许异步，初始目标 10 分钟内产出结果。

### 10.3 可靠性

- 手机采集失败可重试。
- 原始数据和AI结果分层存储，避免AI失败影响业务记录。
- 所有外部导入任务有状态：待处理、处理中、成功、失败、部分成功。
- 设备离线和同步延迟要告警。

### 10.4 可扩展性

- 租户、规则、知识库、销售流程都要配置化。
- AI能力通过任务队列扩展，不直接耦合页面请求。
- 电话、微信、广告平台、物流作为独立接入源。

## 11. 技术架构建议

### 11.1 分层架构

- 接入层：手机Agent、广告平台导入、订单物流导入、API/Webhook。
- 数据治理层：清洗、脱敏、客户匹配、去重、时间线合并。
- 业务层：租户、组织、线索、客户、商机、沟通、订单、任务。
- AI层：转写、摘要、信号识别、风险检测、建议生成。
- 应用层：销售端、管理者端、管理后台、商业化后台。
- 审计与监控层：操作日志、同步健康、模型结果质量、异常告警。

### 11.2 数据模型建议

核心表建议：

- `tenants`
- `users`
- `teams`
- `roles`
- `devices`
- `leads`
- `customers`
- `contacts`
- `assignments`
- `communication_records`
- `call_records`
- `wechat_messages`
- `opportunities`
- `customer_stage_events`
- `ai_insights`
- `ai_signals`
- `risk_alerts`
- `tasks`
- `orders`
- `logistics_records`
- `ai_rule_configs`
- `privacy_policies`
- `audit_logs`
- `datasource_sync_jobs`

关键原则：

- 核心表必须有 `tenant_id`。
- 电话和微信原始数据不要直接被AI结果覆盖。
- AI结果单独存储，带 `source_record_id` 和置信度。
- 人工确认结果单独记录，保留AI原始判断。

### 11.3 数据闭环

```text
销售手机/外部平台
  -> 数据接入
  -> 原始数据存储
  -> 清洗脱敏与客户匹配
  -> 沟通时间线
  -> AI分析
  -> 客户/待办/风险/报表
  -> 销售执行与管理督导
  -> 新数据再次从手机回流
```

### 11.4 AI闭环

```text
原始沟通记录
  -> 转写/文本解析
  -> 信号识别
  -> 摘要/建议/风险
  -> 用户确认/修正/忽略
  -> 规则调整/模型评估
```

## 13. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 手机数据采集不稳定 | AI分析和时间线不可用 | 做同步状态、失败重试、异常队列 |
| 电话/微信客户匹配错误 | AI建议误导销售 | 引入低置信度待确认机制 |
| 多租户后补 | 后期重构成本极高 | P0 建 `tenant_id` 和租户上下文 |
| AI结果不可追溯 | 用户不信任AI | AI结果必须绑定来源记录 |
| 敏感数据泄露 | 严重合规风险 | 权限、脱敏、审计 P0 |
| 管理者只看报表不处理 | 管理闭环断裂 | 风险必须有处理状态、责任人和关闭机制 |
| 功能范围膨胀 | MVP延期 | P0只做手机数据、客户、AI建议、管理风险闭环 |

## 14. 开放问题

- 销售手机 Agent 的实现方式：系统级采集、企业微信/微信生态接口、还是定制手机管控方案？
- 微信消息采集的合规授权边界是什么？
- 电话录音是否全部保存，保存周期多久？
- AI分析是否使用外部模型，数据是否允许出租户/出内网？
- 客户匹配以手机号、微信号、公司名、联系人名的优先级如何定义？
- 是否需要兼容已有 CRM，还是只做轻CRM？
- 租户级数据备份、删除、导出策略如何设计？

## 15. 推荐开发顺序

最推荐的开发顺序：

1. 多租户、权限、脱敏、审计底座。
2. 手机设备绑定和数据接入。
3. 客户、线索、沟通时间线。
4. AI摘要、意向、风险识别。
5. 销售工作台。
6. 管理者风险看板。
7. 漏斗诊断、AI参谋、订单物流。
8. 商业化租户后台、套餐计费。

核心原则：先让“数据从手机来、AI能分析、销售能执行、管理能干预”这条主链路闭环，再扩展培训、提成、商业化运营等外围能力。
